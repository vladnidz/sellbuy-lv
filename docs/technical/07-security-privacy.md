# 07 — Security, privacy, and compliance controls

Status: Draft · Owner: tech lead with security lead and legal · Last change: 15 Oct 2026

## 1. Scope and approach

This document defines the technical controls for SellBuy.lv. It follows OWASP ASVS level 2 for web applications, the OWASP API Security Top 10, and GDPR privacy-by-design principles. Legal interpretation is for the lawyer (Q-01, Q-10, Q-11); this document states the technical controls the law is expected to require.

Penetration tests are required before R2 (payments, personal data) and again before R3 (auctions).

## 2. Authentication

### 2.1 Methods

| Method | Level granted | Notes |
|---|---|---|
| Smart-ID | L2 | Strong authentication. Personal code is never stored in plain text (section 6.1). Verified name stored only with consent. |
| Phone OTP (SMS) | L1 | Six-digit code, 5-minute validity, 5 attempts, rate limited per number and IP. |
| Email magic link | L0 | Single-use token, 15-minute validity, hashed at rest, bound to the requesting browser via a short-lived cookie. |
| Passkeys (R2 or later) | Optional second factor or primary | Only after the owner approves. |

### 2.2 Sessions

- Session token: 256 random bits, generated by a CSPRNG. Only the SHA-256 hash is stored (`Session.tokenHash`).
- Cookie: `__Host-session`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`.
- Idle timeout: 30 days (rolling, refreshed at most once per hour). Absolute timeout: 90 days.
- Rotation: on sign-in, on method change, on privilege change (for example, verification upgrade), and every 24 hours for staff sessions.
- Staff sessions: idle timeout 8 hours, absolute 12 hours, two-factor authentication required (TOTP or passkey), IP prefix recorded.
- Revocation: "sign out everywhere" revokes all sessions except the current; password-like events (method removal) revoke all sessions.
- New-device notice: email sent when a session is created from a device fingerprint not seen in the last 90 days.

### 2.3 Account recovery

- Responses to recovery requests are identical whether or not the account exists.
- Recovery links expire in 15 minutes. Recovery codes are not used.
- Seven-day block on recovery after a reported account takeover.

## 3. Authorisation

### 3.1 Model

- Role-based for staff and company members; attribute-based for ownership and verification level.
- Single policy module: `packages/domain/policy/`. Every service function calls the policy with `(actor, action, resource)` before any read or write.
- Deny by default. A policy function returns `allow`, `deny` with reason code, or `conditional` with a missing requirement (for example, verification level).

### 3.2 Rules that must have negative tests

- Users can read and change only their own drafts and listings, unless acting for a company role that permits it.
- Buyers and sellers can read an order only if they are a participant. Staff read orders only with a case reference.
- Messages are readable only by the two participants. Moderators read messages only in an assigned case, with a logged reason and a time limit.
- Auction bids: seller cannot bid; linked accounts cannot bid on the seller's auctions.
- Company actions require the company role. Owner-only actions: billing, API keys, ownership transfer, member removal of owners.
- Finance actions require a finance role; approvals require a second person.
- Insecure direct object references: every ID in a path is checked against the caller's scope, even when the ID is a UUID.

### 3.3 Staff access

- Separate staff login, two-factor required.
- Least privilege per role. Access reviews quarterly; access removed within one working day of role change.
- Every personal-data view is logged with user, time, reason code, and case reference.
- Break-glass access for production incidents: time-limited, two-person approval where possible, reviewed within one working day.

## 4. Input handling and output encoding

- All inputs validated at boundaries with Zod schemas. Unknown fields rejected for write endpoints.
- Text fields stored as plain text. Rendering escapes by default (React). Markdown and HTML are not accepted in listings, messages, or reviews.
- Links in messages are not clickable unless they point to an allow-listed domain (SellBuy and official carriers only). Link text is shown as text.
- SQL: parameterised queries only. Raw SQL statements live in named files with tests.
- File names are never used in storage paths. Storage keys are random.
- Server-side request forgery protection for any URL-based import (bulk upload images): allow only HTTPS, resolve DNS and reject private, loopback, and link-local ranges, cap redirects at 2, limit size and time.
- Bulk upload parsing: CSV and XLSX parsed with limits (maximum rows, maximum cell size, no macros, no external links, no formula evaluation).

## 5. Uploads

- Accepted image types: JPEG, PNG, HEIC, WebP. Content type detected by file signature, not extension.
- Maximum size: 15 MB per image as sent; 20 images per listing (see business rules for other levels).
- Processing pipeline: signature check, decode into a sandboxed image library with memory and pixel limits (decompression bomb protection), EXIF removal, re-encode to WebP and AVIF, thumbnails, perceptual hash, safety classifier score.
- Stored in a private bucket. Public variants in a separate bucket with unguessable keys. No public listing of the bucket.
- Documents (for example, technical inspection, declaration of conformity): PDF, JPEG, PNG; maximum 10 MB; scanned for malware before access; available only to the seller and to staff with a case reference.
- Downloads use short-lived signed URLs (5 minutes).

## 6. Personal data

### 6.1 Identifiers and sensitive fields

| Data | Storage | Access | Notes |
|---|---|---|---|
| Smart-ID personal code | Keyed hash (HMAC-SHA256 with a secret in the secrets manager). Never plain text. | Not readable by anyone; used for matching only | Hash key rotated under a documented procedure; rotation requires re-hashing, planned as a migration |
| Phone number | Encrypted at rest (application-level envelope encryption) | Owner; staff with case reference | Shown to others only through phone reveal (logged) |
| Email | Encrypted at rest | Owner; staff with case reference | Not shown publicly |
| Verified name | Encrypted at rest | Owner; shown only with consent | |
| IBAN | Encrypted reference; masked display | Owner; finance staff for payouts | |
| Postal address | Encrypted at rest | Owner; shipping partners for shipment; finance for invoices | |
| IP address | Prefix (for example first three octets for IPv4, /48 for IPv6) in session and audit tables; full address in access logs for 30 days | Security staff | |
| Device fingerprint | Hashed | Security staff | Used for fraud and linked-account signals |
| Message content | Stored with the conversation | Participants; moderators in case with reason; never by support without consent or legal requirement | |
| Photos | Public variants have metadata removed; originals private | Owner; moderators in case | |

### 6.2 Keys and encryption

- Encryption at rest: managed database encryption plus application-level envelope encryption for the sensitive fields in 6.1.
- Data encryption keys wrapped by a key-encryption key in the managed key service. Keys rotated annually; rotation is tested in staging.
- TLS 1.2 minimum, TLS 1.3 preferred, HSTS enabled, certificate monitoring.

### 6.3 Logging rules

- Logs are structured JSON. Personal data is not logged. The logger has a redaction list: email, phone, personal code, IBAN, address fields, token-like strings, card-like numbers, names in free text where possible.
- Error reports to Sentry: personal data scrubbing enabled; user identifiers are internal IDs only.
- Analytics events contain IDs and categorical values only. No names, emails, phones, free text, or search terms in analytics (see `06-search.md` section 11).
- Logs are reviewed for leakage in each release (automated test with planted personal data).

### 6.4 Data subject rights

| Right | Mechanism | Time limit |
|---|---|---|
| Access and portability | Data export (US-01.08) | 30 days maximum; target minutes |
| Rectification | Profile and listing edit; support for verified corrections | Without undue delay |
| Erasure | Deletion with 30-day cooldown; anonymisation; retention exceptions for legal records | Completed within one month of cooldown end |
| Restriction | Support request; account hold | Without undue delay |
| Objection (marketing) | Preference centre; one-click unsubscribe | Immediate |
| Withdraw consent | Settings | Immediate |

### 6.5 Retention schedule

| Data | Period | Action at end |
|---|---|---|
| Account and profile | While active; 30-day cooldown after deletion request | Anonymise |
| Listings (deleted by user) | Removed at deletion | Hard delete |
| Listings (expired or sold) | 2 years for dispute and tax reference | Anonymise seller; keep item data |
| Messages | With the conversation; removed or anonymised on account deletion | Hard delete or anonymise |
| Orders, invoices, payments, ledger | As required by Latvian accounting law (confirm, Q-04; proposal: 10 years for accounting records) | Retain; restrict access |
| Disputes and evidence | 3 years after closure (proposal) | Delete evidence files; keep decision record |
| Moderation cases | 3 years after closure (proposal) | Anonymise |
| Reports | 2 years | Delete |
| Audit logs (money, staff, auctions) | 5 years | Delete |
| Audit logs (other) | 1 year | Delete |
| Access logs with IP | 30 days | Delete |
| Session records | 90 days after expiry | Delete |
| Consent records | Life of account plus 3 years | Delete |
| Backups | 35 days rolling | Overwritten |
| Search zero-result queries | 90 days | Delete |
| Drafts | 60 days without changes | Delete |
| Image originals (unused) | 24 hours without reference | Delete |

Deletion jobs run daily in the worker and log counts without identifiers.

## 7. Abuse and rate limiting

- Limits per IP and per account, implemented at the edge and in the application (`03-api.md` section 4).
- Login and OTP endpoints use progressive delays and temporary blocks after repeated failures.
- Bot detection on sign-up and on message bursts; challenge with a non-personal-data CAPTCHA only when needed.
- Scam-pattern detection in messages (US-05.07): phrases and behaviours, not message content stored outside the conversation.
- Automatic restrictions only through the enforcement ladder; automatic actions always create a case for review.

## 8. Web security headers and browser controls

- Content-Security-Policy: default-src 'self'; script-src with nonces; img-src 'self' and the public media origin; frame-ancestors 'none'; connect-src limited to API, realtime provider, and analytics origins.
- Strict-Transport-Security with preload after the owner approves.
- X-Content-Type-Options: nosniff; Referrer-Policy: strict-origin-when-cross-origin; Permissions-Policy: restrict camera, microphone, geolocation to the features that need them (photo upload uses file input and does not need the camera permission).
- CSRF: SameSite cookies plus a double-submit token on state-changing requests; origin checks on all POST, PUT, PATCH, DELETE.
- CORS: none for cookie-based routes; API keys only for business routes with explicit origin lists.
- Subresource integrity for any third-party script (the design avoids third-party scripts except payment provider hosted fields and consented analytics).

## 9. Secrets and configuration

- Secrets in the managed secrets store. Never in code, images, logs, or environment files committed to the repository.
- Each service has its own identity and credentials. Database roles: `sellbuy_web` (no DDL), `sellbuy_worker` (job tables and domain writes), `sellbuy_migrator` (DDL, used only in the release pipeline), `sellbuy_readonly` (reporting).
- Secret scanning in CI on every push. Pre-commit hook optional.
- Rotation: API keys 90 days; webhook secrets 90 days; database passwords 180 days; signing keys annually.

## 10. Supply chain

- Lockfile committed. Dependencies pinned. Automated updates reviewed weekly.
- Dependency scanning in CI; high and critical advisories block release unless accepted with an expiry date.
- Software bill of materials generated on release.
- Build provenance attestations for the worker and web images.
- Third-party scripts and fonts self-hosted where possible.

## 11. Monitoring and incident response

- Security events: failed logins, OTP abuse, role changes, staff access to personal data, payout approvals, bid anomalies, webhook signature failures.
- Alerts routed to on-call. Severity definitions in `09-testing-release-ops.md`.
- Incident process: detect, contain, assess (personal data involved?), notify (data protection authority within 72 hours where required; affected users without undue delay where risk is high), remediate, review.
- Breach notification template and decision tree maintained by legal (Q-10).
- Runbooks: account takeover, credential stuffing, data exposure, payment fraud spike, stolen-goods campaign, webhook compromise.

## 12. Trust and safety technical controls

- Image safety classifier (adult and violent content, weapons, drugs): threshold-based; uncertain images go to review.
- Prohibited-word and pattern lists versioned and reviewed monthly.
- Duplicate and stock-photo detection with perceptual hashing.
- Stolen-goods checks for phones (IMEI) and vehicles (VIN) through a lawful provider (Q-08).
- Fraud scoring signals and thresholds documented in the model card; decisions are reviewable.
- Human review for every automated removal of a seller's listing that was previously approved, unless the content is clearly illegal.

## 13. DSA controls (online marketplace)

- Notice-and-action: a visible mechanism to report illegal content; confirmation to the notifier; decision to the uploader with reasons; complaint route (US-15.03).
- Trader traceability (Article 30 of the Digital Services Act): for traders (professional sellers), collect name, address, contact, identity document or equivalent, bank account, and registration number where applicable; make reasonable efforts to check accuracy; display where required; suspend trader if information is incomplete after notice.
- Transparency reporting: annual report on notices, removals, complaints, and automated decisions.
- Recommender system transparency: ranking factors and options to change ordering where feasible (see `06-search.md`).
- Advertising transparency: labels, advertiser identity, parameters used for targeting (where relevant to paid promotions).
- Points of contact and legal representative details published as required.

Legal review required on the exact application to SellBuy (Q-09 and related questions).

## 14. Threat model (summary)

| ID | Threat | Likely vector | Primary controls | Residual risk |
|---|---|---|---|---|
| T-01 | Account takeover via phone or email | Phishing, SIM swap, credential reuse | Smart-ID for L2; new-device notices; recovery block; session revocation | Medium at L0 and L1 |
| T-02 | Seller fraud (fake items, advance payment) | Chat, listings | Verification levels; escrow; warnings; reports; fraud scoring | Medium before R2 |
| T-03 | Buyer fraud (chargeback abuse) | Payment disputes | Escrow evidence; dispute workflow; fraud scoring; provider tools | Medium |
| T-04 | Auction manipulation (shill bids, sniping) | Linked accounts | Linked-account rules; anti-sniping; audit; review holds | Medium |
| T-05 | IDOR exposing messages or orders | API misuse | Policy module; negative tests; participant checks | Low with tests |
| T-06 | Data leak from database | Credential leak, misconfiguration | Least privilege; encryption; no personal data in logs; network restrictions | Low to medium |
| T-07 | Malicious upload (malware, decompression bomb) | Upload endpoints | Signature checks; sandbox decode; limits; scanning for documents | Low |
| T-08 | SSRF via image URL import | Bulk upload | Allow-list schemes; private range block; redirect limits | Low with controls |
| T-09 | XSS through listing or message content | Stored content | Plain text only; escaping; strict CSP | Low |
| T-10 | Webhook spoofing | Public endpoint | Signature verification; idempotency; IP allow-list where provider supports it | Low |
| T-11 | Insider misuse of personal data | Staff | Least privilege; logged views; reason codes; quarterly reviews | Medium |
| T-12 | Stolen goods listed | Listings | IMEI and VIN checks; reports; M2 queue; law-enforcement process | Medium |
| T-13 | Scraping of listings and personal data | Automated clients | Rate limits; bot detection; no personal data in public pages; terms | Medium |
| T-14 | Denial of service on bidding | Traffic spikes at auction close | Rate limits per user; queue smoothing; edge caching of public auction state; capacity plan | Medium |
| T-15 | Supply chain compromise | Dependencies | Lockfile; scanning; provenance; review | Low to medium |

## 16. Compliance checklist (before public launch)

- [ ] Privacy policy and terms reviewed by Latvian counsel (Q-01).
- [ ] Record of processing activities complete.
- [ ] DPIAs completed for Smart-ID, moderation with AI, fraud scoring, price intelligence (Q-10).
- [ ] Data protection officer decision recorded.
- [ ] Cookie consent implemented and tested.
- [ ] Accessibility statement published (European Accessibility Act, US-15.08).
- [ ] DSA notice-and-action, complaint route, and statement of reasons implemented (US-15.03).
- [ ] Trader traceability design approved (US-15.04).
- [ ] Penetration test (R1 scope) completed with critical and high findings closed.
- [ ] Backups restore test passed.
- [ ] Incident response runbooks published internally.
